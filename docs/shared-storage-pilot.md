# CI 内部文件存储试点

本次从 `gpu-q-2.1.2` 的 `d7a0191a7aa7aaf0038ca8a4a7169cf0d84aba1b`
起草可选 SSH 存储契约。目标是将可信工作流的内部文件传输移出 GitHub artifacts，
保持测试结果、调度、GPU 资源回收和旧工作流兼容。当前交付为 P0 设计草案，
接口与配置尚未实现；本文件不是部署完成记录。

以 [design.md](design.md) 的 optional SSH storage 提案为契约。
`parallel/examples/storage.example.toml` 仅展示拟议配置格式，不能交给当前部署器执行。
真实地址、账户、目录、SSH 别名及凭据留在私有运维记录和主机私有配置中。

## 以当前分支核对实施入口

2.1.2 同时保留 schema 1 与 schema 2，不能只替换 `actions/part`。
schema 2 已经有中央调度器、执行器和组织模式；沿用现有认证与控制通道，
SSH 仅承担文件传输，不替换调度协议，也不新增凭据签发服务。

- `.github/workflows/ci-v2.yml` 目前上传计划文件并把 artifact ID 交给 `submit`。
  `parallel/scheduler.py` 会通过 GitHub 核对归属；新后端必须成对修改上传与核验。
- `parallel/workflow_client.py` 的 `fetch` 目前按 artifact ID 下载计划文件，
  在此之前会检查 checkout 和测试 SHA。新读取路径保留这些检查与安全解包限制。
- `.github/workflows/execute.yml` 目前上传 `ci-allocation-<id>`。
  `collect_allocation_results` 负责收集结果与项目报告；存储失败须由必需步骤明确报错。
- `parallel/github_coordinator.py` 当前以执行 job 完成和 GitHub artifact 存在作为证据。
  内部后端必须独立核验完成清单，并与执行器结果比对，不能只跳过 artifact 检查。
- `parallel/scheduler_store.py` 分别记录资源释放与 runner 完成。
  上传成功不能提前释放资源，资源释放也不能代替结果发布或 job 完成。
- schema 1 的 `part`、`artifacts`、`verdict`、`flow` 与 salvage 同步适配，
  不改变 `artifacts.current` 的重跑选择，也不改变真实测试失败的判定。

## P0 当前准备状态

维护工作站已验证四个设备角色均可通过指定凭据登录，角色为 `3090a`、`3090b`、
`pro6000`、`h100`。只读检查确认均有 SSH、SFTP、rsync、timeout 与 Python 3 命令。
这些检查只证明工具存在，不证明 Python 版本合适、主机之间认证可用或目录可读写。
已核对现有 runner 服务中的 CI 配置入口，真实路径不进入本文件。

本次只读探测中，`3090a` 与 `3090b` 双向的默认 SSH 认证均被拒绝；
`pro6000`、`h100` 到存储候选端的严格主机指纹校验均因缺少已知指纹而拒绝。
这不排除现有专用通道可复用，但当前默认通道没有通过验收。
四台已核对的既有 hook 引用均为 `v1.22.0`；这只描述该入口，不能推断
其他部署目录的 v2 状态。将源码切到 2.1.2 不会自动升级这些运行入口。

首轮建议 `3090a` 为集中存储端，`3090b` 为异机生产者和消费者。
控制端需要独立读取并验证计划与分配结果；执行端需要上传结果、读取计划。
其他设备依次接入。Slurm 保留既有 gate 和回传链路，由持有本次授权的本地驱动端
接入新存储，不向集群额外分发存储密钥。公开及 GitHub-hosted 路径保持现状。

P0 在负责人评审前完成以下材料：

- 可评审的后端接口、命名空间、完成协议和配置格式。
- 与 2.1.2 实际入口对应的修改范围，以及新旧后端兼容和回滚限制。
- 只读登录、工具与 CI 配置位置核对；主机间默认 SSH 认证探测单独记录结果。
- 存储角色、账户、目录、密钥接入与负责人决策清单；真实清单保留在私有记录中。

跨机真实上传下载与原子发布属于 P1。未配置并验证认证与专用目录前，
不能将工作站登录成功记为文件通道验收通过。

## P1 通道验收

负责人先确定专用 CI 根目录、容量上限、备份与故障责任，并审阅私有接入清单。
允许复用现有 CI 账户与普通 SSH 密钥；工作站私钥不会自动复制到服务器。
如需新增密钥、修改 `authorized_keys`、服务或定时器，先列出具体变更交负责人批准。
部署前附上各涉及主机的 `setup/plan.sh` 输出和拟变更清单。
旧版 setup 计划不包含新存储能力，不能把空计划当成新能力已部署的证据。

通道通过标准是 runner 直接传输，不经维护电脑中转：

1. 双向上传下载小文件和接近所设上限的文件，记录字节数、摘要与耗时。
2. 两个并发发布者发布相同内容应幂等；不同摘要应有明确冲突，不能覆盖。
3. 中断上传后消费者看不到半成品；发布成功但确认丢失后重试得到同一引用。
4. 验证目录不可写、主机指纹不符、认证失败、超时、损坏和空间不足均明确失败。
5. 证实路径限制、完成目录的原子发布、锁与 flush 在所选文件系统生效。
6. 查看公开输出不含站点、账户、路径或原始 SSH 错误；私有记录保留诊断证据。

## P2 实现与测试

契约通过后分别实现存储协议、v2 生产消费闭环、schema 1 适配及项目读取端。
先增加支持，再启用配置。配置独立于现有 inventory 和 central 配置，避免旧加载器
因陌生字段拒绝当前服务。部署导出须明确处理每台主机自己的存储配置与密钥路径，
不得将控制端 PAT 或其他设备凭据带入执行端。

测试必须覆盖仓库、运行、run attempt、task attempt 和 allocation 之间的隔离，
清单身份与摘要不符、丢失完成标记、并发冲突、恶意 ZIP、总时限、断线重试、
控制端重启与结果发布恢复。每个新增测试附能被其杀死的变异。
v2 还要覆盖 plan-only、空计划、完整重跑、组织模式字段过滤、GPU 租约不提前归还、
Slurm 驱动端上传、job 完成与存储核验两份证据，以及已通过命令的发布失败不能变绿。
v1 保持既有 artifact 解析、重跑选择、补救与最终汇总回归。

## P3 至 P5 推广

选择可信的 BrainMass CPU 小工作流先闭环。先核对它当前调用 v1 还是 v2，
再使用对应路径；不为存储改造隐式迁移调度协议。对同一提交记录依赖、
硬件、用例收集数、通过、失败、跳过和耗时，验证真实失败、发布失败、读取失败、
允许的基础设施重试及完整重跑。内部文件链路不再请求 GitHub artifact 上传或下载。

随后迁移 BrainCell，再迁移 BrainSpike 的计划、分片、覆盖率、GPU、映射与 Nightly。
逐项核对项目脚本的下载与跨运行索引，生产者和消费者必须成对切换。
跨运行 test-map 与 impact-map 保留分支、祖先和多映射合并规则，
Nightly 整体失败不能直接成为删除其映射的理由。至少一个完整 Nightly 和一次重跑
验收通过后再扩展。已有文档包保留策略不重做。

清理先 dry-run，只列候选、原因与受保护依赖。配置中的期限是候选最小年龄，
活跃运行、重试宽限、恢复记录、读取租约、人工保留和映射依赖仍受保护。
无法确认终态或依赖时跳过。TTL 删除另行批准启用，本次不删除既有 GitHub 数据。
上线后观察七天实际新增字节、驻留时间和磁盘占用，不使用旧快照承诺固定收益。

回滚先停止扩大启用，让在途运行按其已绑定的后端完成或明确取消，
仅新运行切换后端。GitHub 额度不足时暂停受影响工作，不承诺切回即可恢复。
保留所有已发布证据以便恢复和复核，不自动清空目录。
