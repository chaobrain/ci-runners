# 共享存储现有账户与通道复用评估

状态：2026-11-24 只读核对后的设计修订，待按本方案适配实现；未部署。
本页优先于旧的 [P1 多账户部署候选](storage-p1-deployment.md)。
计划书要求访问隔离、结果完整性和最小权限，没有要求新增三个 Linux 账户。
存储、授权签发、传输是逻辑职责，不自动等于三个新账户。

## 结论

优先复用专用机器上已有的维护账户，在其受保护目录中部署按连接启动的受限
文件网关。维护者已确认该账户可以限定为维护和可信服务，不运行项目测试或
其他非信任代码。现有 CI 运行账户继续执行测试；它不能获得维护账户的密码、
普通登录密钥、授权签发私钥或通用文件访问权。

P1 首轮由 3090a 的既有维护账户承载网关，3090b 用现有 CI 账户探测合成数据；
由维护端离线签发限定在合成命名空间的授权。先不新建存储、签发、探测系统
账户，也不把多个职责都交回 CI UID。这个简化试点不能被当作真实多仓库 CI
运行间隔离已经通过验收。正式接入前仍需完成下文的可信代理和本地结果边界。

## 已核对的事实及证据限度

- 3090a、3090b、6000pro 均存在维护账户，UID 与各自 CI 运行账户不同。
  从 CI 身份核对，不能进入或写入该维护账户的 home；home 的 mode 为 0750，
  其父路径由 root 拥有且不能由 CI 身份写入。真实账户、UID 和路径仅在私有证据。
- h100 没有这个维护账户，其执行服务仍处于原有共享账户。此处不因本修订给
  共享账户发放可持久跨仓库访问的存储权限。
- 已用维护账户成功登录 3090a。该账户可以管理自己的 mode 0700 SSH 目录、
  mode 0600 授权文件和用户配置目录；未修改任何内容。目前没有建立可用于本次
  部署的管理员执行通道；用户目录安装和按连接启动可与系统级部署分开考虑。
- 3090a 的维护账户当前未开启 linger，也没有已加载的 CI 用户服务。
  这是一次快照，不证明该 UID 历来只运行可信代码；维护者确认的用途限制是
  复用前提。按连接启动网关不依赖持续的用户管理器；常驻代理另行核对生命周期。
- 既有 scheduler/executor 均运行在 CI 执行 UID 下；h100 则在共享 UID 下。
  将私钥交给这些同 UID 服务不构成与 checkout 代码隔离。
- 既有 pool-probe 专用凭据可以完成受限状态查询；它们的 forced command
  不是文件网关。此前 11/12 个方向返回状态 JSON 的证据不能转换成文件访问授权。

账户用途、进程列表与路径 mode 都不是完整安全证明。部署前还需复核 ACL、
每级父路径、共享挂载、组成员、普通维护登录方式以及真实任务的进程/目录边界。

## 逐项评估

### 直接复用 CI 账户与通用 SSH 或共享目录

不选作正式方案。同一 UID 下的任务可以读同账户密钥、接触同 UID 服务或
修改同 UID 可写文件；简单增加目录层次、mode 0700 或短有效期不能解决。
原有模型/数据集 NFS 也不能作为 CI 临时数据目录。
在明确独立、仅有合成对象的试点命名空间内，现有 CI 账户可以做探测客户端；
即便该探测身份或授权被其他任务读到，也不能因此获得真实 CI 数据的权限。

### 复用已有受限 SSH 入口

复用协议、主机密钥校验经验和受限命令模式，保留 org-sync/pool-probe 的用途。
不把原状态查询 key 扩成 shell、rsync 或任意文件读取 key；不复制维护登录
私钥到 runner。新的文件操作权限需要独立且经过批准的受限授权行/入口。
已有 SSH 端口可达或既有认证成功，都不能替代仓库/运行权限的负向测试。

### 复用既有维护账户承载网关

选作优先候选。该账户与 checkout UID 之间已经存在可核对的 OS 权限边界。
把版本化构件、服务配置、验签信任、对象和台账放在该账户的受保护子目录，
避免依赖修改系统 Python、root 配置目录或创建新账户。

新探测 key 仅追加一条带 restrict/from/固定命令的授权行，保留已有维护授权。
不对整个维护账户设置全局 Match User/ForceCommand，不改变它正常的维护登录。
既有普通维护登录属于可信管理员访问，不冒充为受限客户端。密码与普通维护
key 不交给 CI；固定入口不能接受请求自报的程序路径、配置路径或 peer 身份。

受限 key 与客户端身份的对应须由固定授权行/可信启动器绑定，并使用专用的
受保护公钥信任记录。不能把整个现有多 key 授权文件错误地当作只有一个客户端，
也不能只相信客户端自报指纹。多个 key、普通维护 key 与受限 key 的混用测试
是该路线的新验收项。

维护账户自身拥有的程序/配置可由该可信维护域管理，不必概念上强制 root 拥有。
但须由显式选择的服务身份和保护路径建立信任，不能取消所有者/链接/权限检查，
不能让 checkout 传入期望 owner 并据此提升其自身为可信签发方。

### 复用既有维护账户承载受控代理

作为正式 CI 接入的下一层候选：在各专用执行机的维护身份中持有传输权限，
由代理完成指定任务的发布/读取，CI 账户不直接持有长期跨仓库权限。
现有三台专用机均有可评估的维护身份，因此没有默认新建客户端账户的必要。

代理不能仅凭 UNIX peer UID、请求中的 repo/run 字段或 checkout 环境变量签发
授权；同一个 CI UID 可发出相同请求。需独立核验受信任调度分配、任务身份、
允许操作和精确对象引用。现有 v2 Unix socket 主要认证 UID、HTTPS 主要认证
主机/设备，控制请求上限也不是大文件协议；不能直接宣布这些通道已提供该能力。

短期 bearer 或 OIDC 只能作为证据的一部分；同 UID 下相邻任务可能窃取彼此
凭据。还要证明结果进入可信存储前不能被另一任务替换，且代理不接受任意本地
源/目的路径。这可能需要既有执行器的每任务隔离、保护的交接目录或其他经验证
的执行边界；没有证据时停止真实 CI 接入，不把移动私钥位置当作完整解决方案。

### 复用现有内部对象服务

保留为替代方案，目前没有取得可直接使用的 CI 专用服务与授权策略证据。
若已有服务可以提供精确授权、完整性校验、原子发布和受控代理，可评估接入，
不再重复建设 SSH 网关。不能把现有调度 API、普通 NFS 或一个可登录账户等同于
已经部署的对象服务。协议变更先更新契约，不擅自开放匿名目录或放宽存量服务。

## 四台机器的职责与接入顺序

3090a：现有 CI 控制/执行职责保留；新增文件网关优先运行在已有维护身份的
保护域，存储集中于此。P1 签发由维护端离线执行；正式自动签发位置及与存储
程序的职责边界在生产方案中评审，不默认要求再创建一个 Linux 用户。

3090b：先用现有 CI 身份运行仅针对合成命名空间的探测；正式迁移时优先评估
已有维护身份承载的可信传输代理及结果交接边界。

6000pro：P1 不改动；后续按与 3090b 相同的授权和代理契约接入，不发通用
维护登录凭据。只有 CPU/GPU 验收完成才扩大范围。

h100：共享账户维持原路径及其 artifact 配额限制。没有现成受保护身份不表示
必须创建一个；优先评估账户外的可信中继。中继同样必须核验真实任务与数据
范围，不能给共享账户一个仅改名的全仓库存储通行证。

## 对已有 PR 与部署清单的处理

[PR #291](https://github.com/chaobrain/ci-runners/pull/291) 保留为签名授权、严格
framing、精确身份、摘要、重放、原子存储等的合成试点实现证据。它的 root-owned
配置检查、单 key 信任假设、固定 root 路径和角色 UID 模型仍属于旧实现，不能
直接填入既有账户或放松检查后部署。维护端离线签发的工具也需适配并验证，
不能假设现有 Linux-only CLI 已支持维护电脑。

旧私有多账户清单标记为被本评估替代、禁止 apply；保留源提交、制品摘要与
历史测试证据，不删除代码或数据。运行时代码未在本修订中更改，新方案实现
应增加可信 owner profile、多 key 会话绑定、维护端签发与不同 UID 的负向测试。

## 继续实施的验收门槛

先按新信任模型适配并在本地验证，再提交受限授权行与私有路径的具体差异。
修改 authorized_keys、创建 key、持久服务/定时器或其他高影响动作仍列入
Needs the lead，不因复用账户而自动执行。用户目录内按连接运行不等于可以绕过
这些审批，也不意味着需要管理员 sudo 才能进行所有步骤。

P1 必须验证两端直接传输、断线/并发/冲突、摘要和完成标记、跨仓库/run/双重
尝试的拒绝、客户端不能进入维护 shell、CI UID 不能读服务密钥或替换可信构件。
真实 CI 还必须满足代理授权与本地结果隔离；h100、公开 fork 和 hosted 任务
仍维持原有边界。TTL、旧数据删除及文档包策略不在本次修订范围内。
